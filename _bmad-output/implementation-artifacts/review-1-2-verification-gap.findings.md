### `parseMoney` accepts leading-zero text when the parsed magnitude is zero and negatively signed

- **Changed surface:** the round-trip check in `parseMoney`, `src/lib/core/money.ts:378` — `if (String(parsed) !== (text.startsWith('-') && parsed === 0 ? '0' : text)) { throw ... }`.
- **Impacted consumer or site:** `parseMoney` itself is described in its own doc comment as the boundary parser for "every runtime boundary" (`src/lib/core/money.ts:295-298`); any future caller relying on it to refuse malformed/leading-zero `int8` text observes this asymmetry.
- **Existing test evidence:** `Broken-verification gap`. The `REFUSED` table in `tests/money.test.ts:1290-1305` tests leading-zero rejection with exactly one case, `['leading zeros', '008500000']` — a positive-magnitude string. No entry in that table (or elsewhere in the file) exercises a negative-signed, zero-magnitude leading-zero string such as `'-00'`.
- **Missing verification:** an assertion such as `expect(() => parseMoney('-00')).toThrow()`.
- **Demonstration:** For `text = '-00'`, `INTEGER_TEXT` (`/^-?[0-9]+$/`) accepts it, and `Number('-00') === 0` is `true`, so `parsed` is normalised to `0` (`money.ts:370`). At the round-trip check (`money.ts:378`), because `text.startsWith('-')` is true and `parsed === 0` is true, the right-hand side of the comparison is substituted with the literal `'0'` instead of the actual `text`. `String(0) !== '0'` is `false`, so no error is thrown, and `parseMoney('-00')` silently returns `0`. The sibling positive-leading-zero case `'008500000'` is correctly refused by the same line because `parsed` is non-zero there, so the substitution doesn't apply — the test suite verifies only that branch, not the zero-magnitude one.
- **Consequence:** A malformed monetary string with a negative sign and leading zeros parses successfully as `Money(0)` rather than being refused as corrupt input — exactly the class of silent failure the function's own doc comment says it exists to prevent ("a money value that cannot be parsed is corruption or a wiring mistake ... never a rule violation," `money.ts:349-351`).
- **Suggested test shape:** add a case to the `REFUSED` table in `tests/money.test.ts`, e.g. `['a negative zero with leading zeros', '-00']`.

### CLI entry point of the purity gate is never exercised by any test

- **Changed surface:** the CLI guard in `scripts/check-core-purity.js:975-983` — `const invoked = process.argv[1]; if (invoked !== undefined && import.meta.url.toLowerCase() === pathToFileURL(invoked).href.toLowerCase()) { ...; process.exitCode = 1; }` — newly introduced and wired into the build via `package.json:12` (`"build": "node scripts/check-pins.js && node scripts/check-core-purity.js && vite build"`) and `package.json:17` (`"check:purity": "node scripts/check-core-purity.js"`).
- **Impacted consumer or site:** the `build` npm script itself (`package.json:12`), i.e. whatever deploy pipeline runs `npm run build` (the repo targets the Netlify adapter per `tests/structure.test.ts`'s "the stack configuration" describe block) — this is the only path that would ever hit the CLI branch as opposed to calling `checkCorePurity` directly.
- **Existing test evidence:** `Broken-verification gap`. `tests/purity.test.ts`'s "the core as committed" describe block calls `checkCorePurity(readCoreSources())` and `readCoreSources()` directly — it imports only the named exports `checkCorePurity` and `readCoreSources` from `scripts/check-core-purity.js` and never spawns the file as a subprocess. Because the module's own CLI guard compares `process.argv[1]` against `import.meta.url` and vitest's own argv never matches this file's URL, the guard's body (the `if (!result.ok) { ...; process.exitCode = 1; }` branch that actually makes `npm run build` fail) is not entered during any test run — it is only entered when the file is executed as `node scripts/check-core-purity.js`, which no test does.
- **Missing verification:** a test that spawns `node scripts/check-core-purity.js` (or runs `npm run check:purity`) as an actual child process against a fixture containing a real violation, and asserts a non-zero exit code / stderr content — i.e., verifying the CLI guard itself, not just the underlying pure function.
- **Demonstration:** the guard's own comment documents that this exact comparison already broke once ("the comparison is case-insensitive because on Windows the drive letter's case differs between `node scripts/x.js` and an npm-script invocation, and a case-sensitive check silently skips the gate entirely," `scripts/check-core-purity.js:972-974`). If this environment-fragile comparison regresses again (a Node/npm version change, invocation through `npx`/`pnpm exec`, or any wrapper that reshapes `process.argv[1]`), the `if` block is silently never entered, `process.exitCode` is never set, and `npm run build` exits `0` even with a genuine purity violation in `src/lib/core`. None of the tests I read would catch this: `tests/purity.test.ts`'s "the core as committed" test calls `checkCorePurity` directly, bypassing the CLI guard entirely, so it passes or fails independent of whether the CLI wrapper itself still works.
- **Consequence:** the build-time purity gate — the same class of bug the script's own comment says already happened once — could silently stop firing on `npm run build` with no automated test catching the regression, letting a purity violation reach a production build via any pipeline that runs `npm run build` without first running `npm test`.
- **Suggested test shape:** a test mirroring `tests/purity.test.ts`'s "the walk covers the whole core" fixture pattern, but invoking `node scripts/check-core-purity.js` via `node:child_process` against a temp fixture with a real violation, asserting a non-zero exit code and stderr containing the violation.
