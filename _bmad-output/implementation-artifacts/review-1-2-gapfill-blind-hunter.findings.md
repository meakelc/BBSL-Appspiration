# Review Findings — Gap-Fill Pass (scripts/check-core-purity.js, tests/constants.test.ts, tests/money.test.ts, tests/purity.test.ts)

- `FORBIDDEN_MEMBERS` in `scripts/check-core-purity.js` is only checked via `ts.isPropertyAccessExpression` (dotted access), so bracket-notation access such as `Math['random']` or `globalThis['Date']` bypasses the gate entirely — a trivial evasion of a check whose own header comment claims it makes the violation "unreachable rather than merely discouraged."

- `ts.isMetaProperty(node)` matches both `import.meta` and `new.target` (both are `MetaProperty` nodes in the TypeScript AST with different `keywordToken`s), but the violation is unconditionally reported with the message "references import.meta — not portable across runtimes." A `new.target` violation would get a misleading detail string that names the wrong construct.

- `isReference()` explicitly documents that declarations "deliberately count as references" so that e.g. `const process = ...` is refused inside the core — but this same logic also fires on destructured bindings (`const { process } = config;`) and parameter names (`function f(process) {...}`) that merely reuse a forbidden identifier as a local name for something unrelated to the ambient global. This consequence is never demonstrated or locked in by a test, so it's unclear whether it's intended or an accidental false-positive surface.

- No test in `tests/purity.test.ts` exercises bracket-notation forbidden-member access, `new.target`, or the destructuring/parameter-shadowing case above — exactly the kind of "trick" inputs a boundary-enforcing static check is most likely to be evaded by or misfire on.

- The parametrized `'refuses %s'` block in `tests/purity.test.ts` (for `Date.now()`, `Math.random()`, `fetch`, `process`, `crypto`, `setTimeout`, `globalThis`, `import.meta`, dynamic `import`) only asserts `rulesFor(source).length > 0`. It never checks which rule fired, so a checker that misclassified, say, `crypto` as `non-relative-import` instead of `forbidden-reference` would still pass silently.

- `scripts/check-core-purity.js`'s header comment claims it "runs as part of `npm run build`, after the pin gate and before Vite." `tests/purity.test.ts` only verifies the CI workflow contains `deno check` and `npm test` for the *test-suite* wiring — nothing in this content checks `package.json`'s build script actually invokes the gate, leaving the build-time half of that claim unverified.

- The "compile-time guarantees" block in `tests/money.test.ts` relies entirely on `svelte-check`/`npm run check` type-checking the `tests/` directory, since `neverRun()` is deliberately never called under vitest. Nothing in this gap-fill content confirms `npm run check` is configured to type-check `tests/**` (svelte-check setups commonly scope to `src/` only), so these `@ts-expect-error` guarantees could silently stop being enforced without any test noticing.

- `tests/constants.test.ts`'s "is declared exactly once" assertion (`CONSTANTS_SOURCE.match(/GLOBAL_WRITE_LOCK_KEY/g)).toHaveLength(1)`) counts raw textual occurrences, including inside comments. Given the doc-comment-heavy style used throughout this diff (e.g. `check-core-purity.js`), a legitimate JSDoc line referencing the constant by name above its declaration would break this test even though the constant is still declared exactly once.

- The `REFUSED` table in `tests/money.test.ts` covers fractional numbers, exponents, thousands separators, leading zeros, and non-numeric types, but omits a leading-plus-sign string (`'+8500000'`) and a whitespace-padded valid number (`' 8500000 '`) — both coerce successfully via `Number()`, so a gap in `parseMoney`'s digit-matching regex around either form would go undetected.

- `readCoreSources` in `scripts/check-core-purity.js` is exported as a general-purpose recursive directory walker (and is exercised directly against synthetic temp fixtures in `tests/purity.test.ts`), but has no guard against symlink cycles or unexpectedly deep/circular directory structures — low risk in the current repo layout, but a latent hazard for a function reused against arbitrary fixture trees.

- The "walk covers the whole core" test in `tests/purity.test.ts` proves the walker finds a `.ts` file nested under `rules/` and skips a `.md` file, but there's no case for a stray `.d.ts`, `.test.ts`, or `.spec.ts` file placed under `src/lib/core` — worth pinning down whether such files should be included in or excluded from the purity gate, since the current extension check (`entry.name.endsWith('.ts')`) would pull them all in.

- `formatMoney`'s grid-rejection table in `tests/money.test.ts` (`[4_250_000, 250_000, -1_250_000, 1]`) doesn't include a case that combines the minus-sign renderer with an off-grid amount near a value that *is* on the grid (e.g. `-499_999` vs. `-500_000`), so an off-by-one in the grid check specifically on the negative branch has no dedicated regression test.
